# vustbench-app

Испытательный полигон с картой Санкт-Петербурга и таблицей показателей.
Каталог задаётся файлом, значения готовятся заранее. Выбор строки переключает
соответствующий слой на карте. Интерфейс не управляет отдельными расчётами.
Сейчас подключена обеспеченность сервисами через IduEdu и ObjectNat.

## Запуск в Docker

Требуется Docker с Compose. Из корня репозитория:

```sh
docker compose up --build -d
```

- Приложение: http://localhost:8080
- Документация API: http://localhost:8000/api/docs
- Проверка API: http://localhost:8000/api/health

Контейнер сначала подготавливает показатели из каталога, затем запускает API.
Повторный запуск использует готовые результаты, если совпадают исходные данные
и граф. На странице сразу показаны значения; выбор строки меняет карту.

Отдельная команда подготовки всего каталога:

```sh
docker compose run --rm backend python -m vustbench_app prepare
```

Готовый граф IduEdu можно передать флагом `--graph-path /app/artifacts/city.urbangraph`
команды `compute` или переменной `VUSTBENCH_GRAPH_PATH` процесса.
[walk.urbangraph](data/walk.urbangraph) находится автоматически; единственный
архив `.urbangraph` в каталоге данных также распознаётся автоматически.
CLI команды `compute` также принимает `--osm-id`
для выбора территории по OSM relation вместо области, построенной из кварталов.
Для Docker скопируйте [.env.example](.env.example) в `.env` и укажите путь
внутри контейнера. Граф или локальный `.osm.pbf` можно разместить в
[папке данных](data/): она доступна как `/app/data`. Для PBF в примере приведены
переменные `IDUEDU_OSM_SOURCE` и `IDUEDU_PBF_PATH`.

[Исходные данные](data/) монтируются read-only. Производные данные находятся в
именованном Docker-томе `artifacts`: остановка контейнеров их сохраняет.
`docker compose down -v` удаляет этот том вместе с результатами и графами.

Для сохранения копии артефактов на хосте:

```sh
docker compose cp backend:/app/artifacts ./saved-artifacts
```

## Каталог показателей

[indicators.json](data/indicators.json) содержит 114 строк приложения 1 исходного
описания бенчмарка: номер показателя, название, единицу измерения и настройки
расчёта. Таблица приложения показывает эти три поля и значение. Исходная
иерархия групп и подгрупп хранится в `groups`; при открытии страницы все группы
свёрнуты, их раскрытие сохраняется при обновлении значений. Исходная
повторяющаяся нумерация 7.6 сохранена; внутренние идентификаторы уникальны.
Обеспеченность в единицах «б.р.» показывается коэффициентом от 0 до 1.
Для 23 показателей указано прямое соответствие типу сервиса; у 20 есть исходные
слои и готовые результаты. Остальные строки показывают «—». Составные категории,
например общественное питание или социальная помощь, не подменяются одним слоем.
Также поддерживается `for_each: available_service_types` для раскрытия шаблона
по доступным типам из [каталога сервисов](data/bn_service_types.json).

`result_field` выбирает поле сводного результата, `scale` и `precision`
задают представление значения. `map.layer`, `map.overview_layer`, `map.field`,
`map.range`, `map.colors` и `map.overlays` описывают слой и шкалу карты.
Фронтенд получает эти сведения через `GET /api/indicators` и не содержит
ветвлений по школам, детсадам или типу оценщика.

Декларация без `for_each` описывает самостоятельный показатель. Для уже
известного сводного поля достаточно изменить файл. Новый алгоритм подключается
на Python; интерфейс таблицы и выбора слоя остаётся общим. Помимо обеспеченности
поддержан вычислитель `city_statistic` для числовых полей метаданных города.

## Принятые параметры MVP

Нормативы и типоразмеры берутся из предоставленного
[bn_service_types.json](data/bn_service_types.json); пакет BlocksNet не требуется.

| Параметр | Решение |
| --- | --- |
| Население | `population_balanced` из [зданий](data/buildings.geojson), 5 382 888 жителей; `is_living` не отбрасывает население |
| Школьный спрос | 120 на 1 000 жителей |
| Школьная доступность | 15 минут пешком; OD рассчитывается до 45 минут |
| Пропуски школьной вместимости | 300 мест у 148 из 880 объектов |
| Суммарный школьный спрос | 645 947 после округления методом наибольших остатков |
| Суммарная вместимость школ | 496 335, включая оценённые значения |
| Область графа | Выпуклая оболочка [кварталов](data/blocks.geojson) с метрическим буфером 3 750 м для школ |

Пропуски `capacity` заменяются нижней медианой **всех** положительных целочисленных
`units[].capacity`, включая повторяющиеся типоразмеры. Значение выбирается из
каталога, а не выводится из площади контура. Для школы это 300, для детсада 180.
Исходная заполненная вместимость сохраняется; восстановленные значения отмечены
`capacity_estimated` и видны в интерфейсе. Это явно заданное допущение MVP.

Спрос распределяется между зданиями методом наибольших остатков: итог равен
`ROUND_HALF_UP(население × demand / 1000)`, равные остатки разрешаются по ID.
Это предотвращает потерю спроса при усечении дробных значений внутри ObjectNat.

Население и геометрические совпадения не пересобираются. ID привязан к номеру
исходной строки в версии набора данных. `make_valid` исправляет невалидные
геометрии с сохранением строк; пустые геометрии и некорректные числовые значения
дают явную ошибку. Типы без применимого норматива или корректного слоя отключены
от расчёта и не блокируют другие типы.

## Что означают показатели

- Обеспеченность — `sum(supplied_demands_within) / sum(demand)`: доля спроса,
  удовлетворённая в пределах норматива T, а не среднее процентов зданий.
- Дефицит в нормативе — `demand - supplied_demands_within`.
- Нераспределённый спрос — `demand_left`. Назначение дальше T, но до 3T,
  уменьшает нераспределённый спрос, сохраняя дефицит в нормативе.
- Загрузка сервиса — число назначенных потребителей; относительная загрузка —
  отношение этого числа к вместимости.

Школьный спрос измеряет потребность в местах, а не всё население. Распределение
выполняет ObjectNat при `seed=0`. Матрицу времени с подходами к сети строит
IduEdu через `project_objects` и `od_matrix(weight="time_min", cutoff=3*T)`.

Карта получает объекты по bbox и масштабу: кварталы на дальнем масштабе,
здания начиная с zoom 12, сервисы как точки. Ограничение ответа — 12 000 объектов;
частичный показ отмечается сообщением. Показатели панели относятся ко всему
расчёту и не зависят от viewport. Подложку OSM можно отключить.

## Архитектура

- [packages/vustbench-core](packages/vustbench-core/) — самостоятельный пакет:
  входные адаптеры, нормативы, спрос, граф, матрица и обеспеченность.
- [backend](backend/) — FastAPI, CLI, статусы и управление процессом расчёта,
  выдача слоёв. Расчётные формулы находятся в core.
- [frontend](frontend/) — React + TypeScript + Vite + Ant Design + MapLibre.
- [compose.yaml](compose.yaml) — Python 3.12 API и nginx/frontend, постоянный том.
- [constraints.txt](constraints.txt) и [package-lock.json](frontend/package-lock.json)
  фиксируют версии зависимостей для повторной установки.

Core не зависит от HTTP, React или состояния приложения. Для будущего разделения
достаточно перенести пакет в репозиторий `vustbench-core` и сменить источник его
установки. Публичный Python-контракт и методические детали описаны в
[документации core](packages/vustbench-core/README.md).

Полигон принимает подготовленные слои, запускает существующую методику и
визуализирует результат. Сбор исходников, восстановление населения и разработка
научной метрики остаются за владельцами данных и методик.

## Результаты и API

В локальном запуске артефакты находятся в `artifacts/`, в Docker — в томе:

```text
graphs/*.urbangraph         сохранённые исходные графы
runs/<id>/manifest.json     статус, параметры, версии, хеши, показатели
runs/<id>/buildings.parquet результаты зданий
runs/<id>/services.parquet  результаты сервисов
runs/<id>/blocks.parquet    взвешенные агрегаты кварталов
runs/<id>/*.geojson         необязательный экспорт одиночного расчёта
runs/<id>/distances.npz     разреженная матрица конечных пар
runs/<id>/distances.axes.json  ID осей, единицы, семантика отсутствующих пар
runs/<id>/worker.log        журнал процесса расчёта
```

Отсутствующая пара NPZ означает бесконечное время; явно сохранённый ноль —
достижимую пару. При перезапуске API незавершённые задачи помечаются как
прерванные; завершённые результаты сохраняются.

Маршруты интерфейса: `GET /api/city`, `GET /api/indicators`,
`GET /api/indicators/{id}/layers/{layer}`.
Операторские маршруты: `GET /api/service-types`,
`GET /api/layers/{buildings|blocks|services}`, `GET /api/runs`,
`GET /api/runs/{id}`, `POST /api/runs`. Форматы и ограничения — в OpenAPI.

Переменные процесса: `VUSTBENCH_DATA_DIR`, `VUSTBENCH_ARTIFACTS_DIR`,
`VUSTBENCH_GRAPH_PATH`, `VUSTBENCH_OSM_ID`, `VUSTBENCH_MAX_LAYER_FEATURES`.
API ограничивает этап графа 600 секундами и весь расчёт 1 800 секундами;
переопределение: `VUSTBENCH_GRAPH_TIMEOUT_SECONDS`, `VUSTBENCH_RUN_TIMEOUT_SECONDS`.
Для Overpass по умолчанию 120 секунд на запрос и одна повторная попытка;
параметры: `OVERPASS_URL`, `OVERPASS_TIMEOUT`, `OVERPASS_MAX_RETRIES`.
Ограничения всего запуска действуют для API-задач; standalone CLI при необходимости
запускается с внешним ограничением времени.

## Локальная разработка и проверка

Python 3.11–3.14, Node.js 24+. Пример для PowerShell и uv:

```powershell
uv venv --python 3.12
uv pip install -c constraints.txt -e './packages/vustbench-core[test]' -e './backend[test]'
npm.cmd --prefix frontend ci
& ./.venv/Scripts/python.exe -m vustbench_app prepare
& ./.venv/Scripts/python.exe -m vustbench_app serve --host 127.0.0.1
# Во втором терминале:
npm.cmd --prefix frontend run dev -- --host 127.0.0.1
```

Локальный интерфейс: http://localhost:5173. Проверки:

```powershell
& ./.venv/Scripts/python.exe -m pytest packages/vustbench-core/tests backend/tests -q
npm.cmd --prefix frontend run build
```

Тесты включают настоящий маленький UrbanGraph → IduEdu → ObjectNat → файлы
результатов, семантику нулевых/недостижимых пар и диапазона T–3T, целочисленный
спрос, происхождение вместимости, bbox, статусы и ограничения времени задач.
Синтетический тестовый граф не является расчётом показателей Петербурга.
Зависимости и API проверены локально на Python 3.11; Docker использует 3.12.
Пройдено 32 теста, сборка TypeScript/Vite и проверка карты в браузере с
реальными слоями. Также отдельно проверена цепочка native core → CLI-процесс →
сохранённые файлы → HTTP API на маленьком тестовом графе.
Docker runtime не проверен: в текущем окружении нет Docker CLI. Городской
baseline рассчитан на предоставленном пешеходном графе; для школ доля
удовлетворённого спроса в нормативе составляет 61,3451%.

[Данные](data/) не игнорируются Git; производные файлы и окружения игнорируются.
Исходные слои в приложение не встраиваются и в контейнерный образ не копируются.
