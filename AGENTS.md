# VUST Bench: инструкции по работе с проектом

## Задача

Разрабатываем испытательный полигон бенчмарка управления развитием территорий.
Наша ответственность — отображение исходных данных, расчёт и представление
показателей, позднее — сравнение сценариев. Сбор и подготовка исходных данных
не входят в эту зону ответственности. Если не хватает данных или параметров,
сообщить пользователю; не придумывать их молча.

Текущий MVP: карта Санкт-Петербурга и справа таблица готовых показателей.
Базовые значения должны быть рассчитаны до открытия страницы. Выбор показателя
переключает соответствующий слой карты. Сценарность/TDT — следующий этап.

## Архитектура

- Вся расчётная логика на Python через IduEdu и ObjectNat. BlocksNet пока
  не подключать как зависимость; его каталог типов сервисов используется как данные.
- [packages/vustbench-core](packages/vustbench-core/) — независимые вычисления,
  графы и матрицы, обеспеченность, агрегация. Не добавлять зависимости от API/UI.
- [backend](backend/) — FastAPI, настройки приложения, подготовка baseline,
  хранение запусков и выдача данных для интерфейса.
- [frontend](frontend/) — React, TypeScript, Ant Design, MapLibre.
- Позднее core будет выделен в `vustbench-core`, приложение останется
  в `vustbench-app`. Сохранять эту границу уже сейчас.
- Приложение должно запускаться через Docker Compose.

## Интерфейс и показатели

- Использовать компоненты Ant Design с исходными стилями; CSS добавлять для
  компоновки и карты, без собственной дизайн-системы.
- Таблица: **№ показателя, Название, Единица измерения, Значение**.
  Сохранять номера, названия, группы и подгруппы исходного документа.
- Во вкладке «Показатели» группы и подгруппы — сворачиваемые разделы,
  изначально все раскрыты. Таблицы имеют `size="small"`. Обновление значений
  не должно сбрасывать раскрытие разделов, навигацию или выбранный показатель.
- [data/indicators.json](data/indicators.json) — источник деклараций показателей:
  иерархия `groups`, вычислитель, единицы, точность и параметры карты.
  Не зашивать список показателей или сервисные ветвления в компоненты интерфейса.
- Не реализованные показатели показывать как «—», а не как ноль.
  Разделы групп во вкладке «Показатели» не имеют собственного значения
  и не переключают слой карты.
- Обеспеченность с единицей «б.р.» показывать коэффициентом от 0 до 1.
- Шапка приложения: «VUStBench», без названия города.
- Сайдбар занимает всю доступную высоту. Табы закреплены над прокручиваемым
  содержимым; полоса прокрутки и место под неё сохраняются даже при коротком содержимом.
- Вкладка «Критерии» начинается с K_TW, K_ED (пока недоступны) и K_SD.
  Каждый критерий — карточка со значением и шкалой [0,1]. «Показать слой»
  переключает карту, «Подробнее» отдельно открывает следующий уровень.
  Навигация идёт в текущем табе, с возвратом назад и breadcrumbs.
- Иерархия K_SD: группа → тип времяпровождения → жизненная ситуация → сервис.
  Для социальной группы показывать диаграмму четырёх осей (доход/деятельность,
  траты/досуг, развитие, риски), пропуски не отображать как нули.
  Где используются веса, показывать вес вместе со значением.
- [data/social_support.json](data/social_support.json) хранит состав социальных
  групп, зависимости, предварительные веса и TODO по их калибровке.
  Не зашивать веса в Python или фронтенд.
- Не добавлять без запроса технические пояснения, параметры расчёта, историю
  запусков и сообщения вроде «первый расчёт строит граф» в основной интерфейс.
- Критерии в интерфейсе подписывать только названиями, без K_TW, K_ED, K_SD
  и других формальных обозначений. Обозначения остаются в модели и документации.
- Не показывать полноту исходных данных в карточках объектов карты.
  Не добавлять тултипы без явного запроса пользователя.
- Подложка карты монохромная; цветные расчётные слои сохраняют свои цвета.
  По возможности избегать длинных тире в интерфейсе и текстах.

## Данные и расчёты

- Исходные файлы находятся в [data](data/), их разрешено хранить в Git.
  Не менять исходные слои ради исправления расчёта. Производные файлы,
  окружения и кэши не должны попадать в Git.
- Население сейчас брать из `population_balanced` зданий.
- Нормативы брать из [data/bn_service_types.json](data/bn_service_types.json):
  `demand` — спрос на 1000 жителей, `accessibility` — минуты,
  `units[].capacity` — типоразмеры вместимости.
- Сохранённый пешеходный граф — [data/walk.urbangraph](data/walk.urbangraph).
  Использовать его для baseline; не скачивать заново при наличии подходящего графа.
- Пропуски вместимости сейчас восстанавливаются нижней медианой всех
  положительных целочисленных `units[].capacity`, включая повторы.
  Помечать восстановленные значения как оценённые.
- Обеспеченность: `sum(supplied_demands_within) / sum(demand)` в пределах
  норматива доступности. При агрегации не усреднять коэффициенты зданий.
- Не подменять составной показатель одним удобным сервисом. Для неоднозначного
  соответствия согласовать состав и методику с пользователем.
- Повторно использовать результаты только при совпадении исходных данных,
  режима и версии графа. Синтетические результаты не выдавать за городские.
- K_SD пока сохраняет формулу (46) как индекс поддержки: больше — лучше.
  Направление критерия ущерба остаётся TODO; не инвертировать его молча.
- Для условного представителя социальной группы численность группы не нужна.
  Входная обеспеченность по-прежнему зависит от общего населения и вместимости.
- Составные средние используют известные входы с перенормировкой весов,
  сохраняя полноту исходных данных. Для K_SD группы нужны все четыре компонента;
  неизвестный целый компонент даёт `None`, а не ноль. Рабочие места пока TODO.
- На любом пространственном уровне сначала агрегировать обеспеченность
  как сумму удовлетворённого спроса / сумму спроса, затем вычислять от этих
  обеспеченностей жизненные ситуации, компоненты и критерии этого уровня.
  Не усреднять ни квартальные обеспеченности, ни квартальные K_SD для города.
  Городские сервисные входы критериев должны совпадать с показателями города.
  Покрытие населения относится к доступности квартальных слоёв, не служит
  весом городского расчёта. Между социальными группами пока равные веса,
  неизвестные группы исключаются.

## Проверка изменений

Локальное окружение — `.venv`; ограничения зависимостей находятся
в [constraints.txt](constraints.txt). Запуск описан в [README.md](README.md).

```powershell
& ./.venv/Scripts/python.exe -m pytest packages/vustbench-core/tests backend/tests -q
npm.cmd --prefix frontend run build
```

После изменений интерфейса проверить в браузере раскрытие групп, выбор показателя
и переключение карты. Для расчётных изменений выполнять соответствующие тесты;
не пересчитывать весь город, если изменение касается только представления.
Не утверждать, что Docker проверен, если контейнеры фактически не запускались.
